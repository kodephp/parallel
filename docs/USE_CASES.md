# 使用场景与选型指南（v1.18.0）

本文回答三个实际问题：

1. **我的业务该用哪个 API**（多线程 / curl_multi / 干脆别并行）
2. **配多少线程、批多大**（附本机实测网格）
3. **哪些业务不能随便并行**（分佣结算、同账户串行、秒结 vs 定时）

所有数据来自本仓库 `benchmarks/` 下脚本，环境：PHP 8.3.33（ZTS）+ ext-parallel，11 逻辑核心，2026-08-10。

---

## 一、30 秒选型表

| 你的场景 | 推荐 API | 理由 |
|---------|---------|------|
| 群发邮件 / 站内信 / APP 推送（几万~几十万条） | `WorkerPool::mapBatchSettled()` | 批量合并降低派发开销，逐条容错不连坐 |
| 批量渲染模板、加解密、签名、图片处理 | `WorkerPool::map()`（自动批量，或显式 `mapBatch()`） | v1.14.0 起 `map` 在元素较多时自动批量合并，无需改 API；CPU 密集任务线程数≈核数即可线性加速 |
| 多用户扇出调用第三方 HTTP API（纯等网络） | `CurlMulti::fetch($urls, 16)` | 单进程事件循环，实测 **10~15×**（最优并发 16~32 间波动），内存最省 |
| 请求外部 API **并且**要对响应做重计算 | `WorkerPool::mapBatch()` + 线程内 curl | 请求与计算整体并行 |
| 分佣 / 奖励 / 余额结算（写同一账户） | 见 [§五 分佣结算](#五分佣结算秒结-vs-定时) | 必须按账户分片，组内串行 |
| 单条请求内的少量并行（3~5 个子查询） | `Parallel::run()` / `run_all()` | 任务少，池化不划算 |
| 极短纯内存任务（每条 <1μs） | **不要并行** | 派发成本远大于任务本身 |
| 预排海量任务 / 非阻塞提交 / 生产者远快于消费者 / 协程内派发 | `ThreadPool` | `submit()` 永不阻塞（实测 2 万任务 ≈18ms、0.9µs/submit），N 个常驻线程异步消费；原始吞吐低于 `WorkerPool`（无批量合并） |

## 二、三档数据规模的实测（群发场景）

脚本：`php benchmarks/bench_message.php`（10 线程 / 4 进程 / 批大小 auto）
单条工作 = 模板渲染 + 字段校验 + 摘要签名。

| 数据规模 | 条数 | 串行 | 线程 `map`（自动批量） | 线程 `mapBatch`（批量） | 4 进程 × 10 线程 |
|---------|------|------|----------------------|------------------------|-----------------|
| **短** 推送通知 120B | 50,000 | 1,070,000 msg/s | ≈1.0× * | ≈1.0× * | 1,550,000（1.5×） |
| **中** 站内信 4KB | 20,000 | 118,000 msg/s | 461,000（3.9×） | 473,000（4.0×） | 500,000（4.2×） |
| **大** 富文本邮件 64KB | 2,000 | 8,070 msg/s | 49,800（6.2×） | 51,600（6.4×） | 38,000（4.7×） |

> \* **短数据（单条 <1μs 的模板替换 + md5）并行开销与任务本身同量级**：倍率受调度抖动影响在
> **0.7×–1.4×** 间波动，多次运行 `map` / `mapBatch` 会互相颠倒——这不是稳定负优化，而是「派发 + 序列化」
> 成本吃掉了收益。可复现的批量合并收益见 [BENCHMARK.md](BENCHMARK.md) 的 `bench_batch`：强制逐条 6.4M →
> 自动批量 10.3M（**1.6×**）。结论：**高频短任务直接 `map()` 即可（v1.14.0 起自动批量），不会比 `mapBatch` 差**。

三条硬结论：

1. **短数据并行收益 ≈ 串行（噪声主导）**：单条工作量低于 ~1μs 时，派发/序列化开销与之同量级，
   任何并行模型都只能小幅波动（0.7×–1.4×）。此时真线程的价值不在「更快」，而在「不阻塞主流程」。
   若想稳定提速，应把多条合并成一个稍重的任务（如按账户/按批聚合），让单条工作量升到 μs 级以上。
2. **单进程多线程已足够打满 CPU**：4 进程 × 10 线程（共 40 并行）在中/大数据下并不优于单进程 10 线程，
   还多付了 fork 与 IPC 成本。短数据下 4 进程因「多独立池、锁争用更小」反而偶尔更快，属噪声，不要当作规律。
3. **数据越大，并行收益越高且越稳定**：64KB 富文本邮件下线程模式稳定 6.4×，中数据稳定 ~4×，
   而 120B 通知只能 ≈1×。

> 「原来单进程 3 万条/秒，开 10 线程能不能提升 10 倍」——取决于**单条任务的计算量**：
> 单条越重（如 4KB 模板渲染，串行 11.8 万/s）提速越接近核数；单条轻到 1μs 以下（120B 拼接，
> 串行已 107 万/s），并行不会带来稳定加速。见下节网格。

脚本：`PROFILE=medium php benchmarks/bench_tune.php`（串行基线取 3 轮最快，避免虚高）

| 22（超配） | 631,649 | 591,626 | 603,701 | 557,520 | 443,539 | 602,989 |

### 进程 × 线程（中数据，batch=128）

| 进程 \ 线程 | 1 | 2 | 4 | 8 |
|-----------|---|---|---|---|
| 1 | 80,969 | 149,969 | 282,646 | 466,690（3.6×） |
| 2 | 156,966 | 265,195 | 441,871 | **549,118（4.2×）** |
| 4 | 300,769 | 472,310 | 554,817 | 534,245 |
| 8 | 472,153 | **564,734（4.3×）** | 521,634 | 450,724 |

### 短数据与大数据的最优点

| 负载 | 串行基线 | 单进程最优 | 进程×线程最优 |
|------|---------|-----------|--------------|
| 短 120B × 50,000 | 1,526,345 msg/s | 11 线程 + auto → 1,839,865（1.2×） | 8 进程 × 2 线程 → 2,126,045（1.4×） |
| 中 4KB × 20,000 | 129,232 msg/s | **11 线程 + batch 128 → 672,498（5.4×）** | 8 进程 × 2 线程 → 570,386（4.6×） |
| 大 64KB × 2,000 | 8,205 msg/s | **22 线程 + auto → 54,736（6.8×）** | 4 进程 × 4 线程 → 45,784（5.6×） |

**配置法则**：

- 线程数 ≈ **CPU 核心数**（本机 11）。超配到 2 倍核数没有额外收益，中/大数据反而掉 3~10%。
- 批大小：**默认 auto 即可**（`mapBatch($items, $worker)` 不传第三参）。auto 在短/大数据两档
  直接拿到全场最优，中数据档为最优值的 90%。
- 手工调批时的内存红线：`批大小 × 单条字节数 × 线程数 < memory_limit / 2`。
  64KB × 2048 × 11 会直接 OOM——这也是 auto 默认封顶 1024 条的原因。
- **进程 × 线程 ≈ 核数**。若已用 `kode/process` 起了 4 个 worker 进程，每进程再开 2~3 线程即可，
  不要每进程再开 10 线程（40 并行在 11 核上是净损失）。

## 四、多用户 HTTP 扇出（curl）

脚本：`php benchmarks/bench_curl.php`（本机 Python `ThreadingHTTPServer`，每请求 20ms 延迟，200 请求）

| 方式 | 耗时 | 吞吐 | 相对顺序理论下限（200×20ms=4000ms） |
|------|------|------|---------|
| 顺序 curl | 5434 ms | 37 req/s | 1.4× |
| `CurlMulti` 不限并发（一次 200 连接） | 10019 ms | 20 req/s | **0.4×（反而更慢）** |
| `CurlMulti` 并发 4 | 1370 ms | 146 req/s | 2.9× |
| `CurlMulti` 并发 8 | 700 ms | 286 req/s | 5.7× |
| `CurlMulti` 并发 16 | 395 ms | 506 req/s | 10.1× |
| `CurlMulti` 并发 32 | 270 ms | 741 req/s | 14.8× |
| `CurlMulti` 并发 64 | 2993 ms | 67 req/s | 1.3×（对端过载） |
| parallel 线程 × 8 + curl | 776 ms | 258 req/s | 5.2× |

> 最优并发档在 **16~32** 之间波动（多次运行 x16≈10×、x32≈15× 会互相颠倒），**不要死记某一个数字**；
> 经验值是 **8~32**，上线前用 `bench_curl.php` 在本机扫一遍取最优点。

结论：

1. **纯 I/O 扇出用 `CurlMulti`**：单进程事件循环，无线程/序列化成本，内存占用最低。
2. **一定要限并发**。不限并发把 200 个连接一次性打出去，比顺序还慢 2.5 倍，还会触发对端限流、
   打爆文件描述符。经验值 **8~32**，压测取本机最优点。
3. **线程 + curl 只在「请求 + 计算」时才划算**：如果拿到响应后要解密/解析大 JSON/写库，
   用 `mapBatch` 让请求与计算整体并行。

```php
use Kode\Parallel\Curl\CurlMulti;

// 多用户回调扇出：按 uid 取回结果，限制 16 个在途连接
$urls = [];
foreach ($users as $u) {
    $urls['u' . $u['id']] = "https://api.example.com/notify?uid={$u['id']}";
}

$results = CurlMulti::fetch($urls, concurrency: 16, timeout: 30);

foreach ($results as $key => $r) {
    if ($r['error'] !== null) {
        // 'timeout' 或 curl 错误串；按 key 精确重试
        $retry[] = $key;
        continue;
    }
    handle($key, $r['response'], $r['info']['http_code']);
}
```

> `CurlMulti` 使用**滑动窗口**：完成一个立即补一个，始终保持 N 个在途，不存在「整批等最慢者」的
> 队头阻塞（v1.13.0 相对 v1.12.0 分波实现，并发 16 档提速 5.5 倍）。

## 五、分佣结算：秒结 vs 定时

多级推荐奖励（向上找 N 级推荐人派奖）是最容易在并行化时出事的业务，因为多条记录会**写同一个账户余额**。

### 1. 秒结（实时到账）——不要并行

单笔订单触发的向上派奖，链路只有几级、要求强一致、必须落在同一个事务里：

```php
// 正确：直接顺序处理，几毫秒完成
DB::transaction(function () use ($order) {
    foreach (uplineOf($order->user_id, levels: 3) as $level => $uid) {
        addBalance($uid, $order->amount * rateOf($level, $order->goods_level));
    }
});
```

并行化在这里**只有坏处**：跨线程无法共用事务、派发开销比业务本身还大、还引入并发写冲突。

### 2. 定时批量结算——分段 + 按账户分片

日终/小时级跑批才是并行的用武之地，但必须遵守两条铁律：

**铁律一：同一账户 ID 的所有记录必须落在同一个任务里，组内串行。**
否则两个线程同时 `UPDATE balance` 同一行，要么死锁、要么金额算错。

**铁律二：等级、价格、费率不同的记录不能合并计算。**
不能把同一账户的 N 条记录 `SUM` 成一条再入账——每条的等级系数、商品单价、结算费率都可能不同，
必须逐条按各自参数计算，只是**在同一个任务内顺序执行**。

```php
use Kode\Parallel\Pool\WorkerPool;

// 1) 按账户分组：同账户的记录聚到一起（保证组内串行、组间并行）
$byAccount = [];
foreach ($rows as $row) {
    $byAccount[$row['account_id']][] = $row;   // 等级/价格不同的记录各自保留
}

// 2) 组间并行；线程数 = 核数
$pool = new WorkerPool(11);

$results = $pool->mapBatchSettled($byAccount, static function (array $rows, int|string $accountId): array {
    // 线程内独立建连（连接不可跨线程共享）
    $db = connect();
    $ok = 0;

    // 组内严格顺序：逐条用各自的等级/价格/费率计算，不做合并
    $db->begin();
    foreach ($rows as $r) {
        $amount = $r['price'] * rateOf($r['level'], $r['goods_type']);
        // 幂等键：同一 record_id 重跑不会重复入账
        if ($db->insertIgnoreLedger($r['id'], $accountId, $amount)) {
            $db->addBalance($accountId, $amount);
            $ok++;
        }
    }
    $db->commit();

    return ['account' => $accountId, 'settled' => $ok];
});

$pool->close();

// 3) 逐账户查看结果，失败的只重跑失败账户
foreach ($results as $accountId => $r) {
    if ($r['status'] === 'rejected') {
        $log->error("账户 {$accountId} 结算失败：" . $r['reason']->getMessage());
        $retryAccounts[] = $accountId;
    }
}
```

**分段（sharding）建议**：数据量到千万级时，先按 `account_id % M` 分段，一段一段跑，
每段内再按上面的方式并行。好处是单次内存可控、失败重跑粒度小、可跨机器分配段号。

```php
// 分段跑批：每段 5 万个账户，段内并行，段间顺序（内存与数据库压力可控）
foreach (array_chunk($accountIds, 50000) as $segment) {
    $rows = loadRowsOf($segment);
    settleSegment($rows);   // 内部即上面的按账户分组并行
}
```

## 六、群发通知的完整范式

```php
use Kode\Parallel\Pool\WorkerPool;

$pool = new WorkerPool(11);          // 线程数 = 核数

// 批大小不传 = 自动推导；逐条容错，单个收件人失败不影响同批其他人
$results = $pool->mapBatchSettled($recipients, static function (array $user): string {
    // 线程内没有自动加载器，依赖类请用 WorkerPool 的 bootstrap 参数加载
    $body = renderTemplate($user);
    return send($user['email'], $body);   // 返回消息 ID
});

$pool->close();

$failed = [];
foreach ($results as $key => $r) {
    if ($r['status'] === 'rejected') {
        $failed[$key] = $r['reason']->getMessage();   // ParallelException
    }
}

// 只对失败的收件人重试，避免整批重发造成骚扰
if ($failed !== []) {
    retryLater(array_keys($failed));
}
```

要点：

- **`mapBatchSettled` 而非 `mapBatch`**：群发场景不允许一个坏地址让整批失败。
- **幂等**：发送前写「发送中」标记或用消息唯一键，重试不会重复投递。
- **限速**：对第三方通道（短信/邮件网关）要限并发，把线程数调到通道允许的 QPS 以内，
  或者改用 `CurlMulti::fetch($urls, N)` 直接控制在途连接数。

## 七、线程内的硬约束（务必遵守）

ext-parallel 的线程是**独立解释器**，不是共享一切的原生线程。以下限制会直接导致运行失败：

| 约束 | 说明 | 正确做法 |
|------|------|---------|
| 无自动加载器 | 线程内 `Foo::BAR`、`new Foo()` 可能报类不存在 | 构造 `new WorkerPool(11, null, __DIR__.'/vendor/autoload.php')` 传 bootstrap |
| 资源不可跨线程 | PDO / curl 句柄 / 文件句柄不能传入线程 | 在线程内新建连接，用完即弃 |
| 参数必须可序列化 | 闭包、资源、含闭包的数组都不行 | 只传标量 / 纯数组 / 可序列化对象 |
| 异常不可跨线程 | 原始异常对象会退化为 `Unavailable` | 本库已自动降级重建为 `ParallelException`，原类名见 `getContext()['class']` |
| 无共享事务 | 每个任务是独立连接 | 每个任务自包含事务，配合幂等键 |
| 静态状态不共享 | 单例 / 静态缓存在每个线程各一份 | 需要共享用本库 `Channel` / `Atomic` / `Lock` |

## 八、什么时候**不要**用本库

- 单条任务 < 1μs 且总量不大：串行 108 万条/秒已经够用，并行只会更慢。
- 需要严格顺序的状态机（如按序扣减库存的单账户流水）：先分片到同一任务再串行。
- 纯等待网络且无计算：用 `CurlMulti`，不要开线程。
- 需要强故障隔离（一个任务段错误不能影响其他）：用 `kode/process` 多进程，
  通过 `EngineFactory::register()` 接入（见 `docs/ENGINE.md`）。

## 九、单线程 vs 多线程：真实提速与场景清单

**最常见的误解**：「开并行就更快」。在 ext-parallel 下，是否更快**只取决于单条任务的计算量**，
而「单线程（threads=1）」本身几乎从不提速——它只是把任务搬进一个独立解释器线程里 FIFO 串行执行，
反而多出序列化开销。

以下为 `bench_tune.php` 在本机（PHP 8.3.33 / ZTS / 11 核）的**真实可复现**数据，串行基线取 3 轮最快：

| 负载 | 串行（参考） | **单线程 threads=1** | **多线程 threads=11（=核数）** | 多线程 threads=22（超配） |
|------|------------|---------------------|------------------------------|-------------------------|
| 中 4KB × 20,000 | 129,232 msg/s | **103,386（0.8×，比串行还慢）** | **672,498（5.4×）** | 631,649（5.1×） |
| 大 64KB × 2,000 | 8,205 msg/s | **7,385（0.9×，略慢）** | **53,313（6.6×）** | 54,736（6.8×） |

两条铁律：

1. **单线程（threads=1）≈ 0.8~0.9×：不是提速，是顺序可预测 + 低内存。**
   它的价值在于「需要严格 FIFO、任务间不能乱序、且不想承担多线程调度成本」的场景，不是用来加速。
2. **多线程（threads≈核数）才是提速来源**：中数据 4.8×、大数据 6.0×（相对串行）；
   相对单线程本身约 **5~7×**。超过核数（threads=22）边际递减，纯属浪费。

> **v1.17.0 精炼（纯 CPU 任务扫描，无序列化噪声）**：提速幅度由**单任务计算量**决定，不是线程越多越好——
> - 轻任务（µs 级，如 37µs/个）：最优仅 `concurrency≈4（约 2.4×）`，再加线程因派发/队列争用反而下降；
> - 重任务（数十 ms 级，如 48ms/个）：随核数线性扩展，`concurrency=11→5×`、`22→6.4×`。
> 故「把线程数堆到核数」只对**重任务**成立；轻任务堆线程是浪费。详见 [BENCHMARK.md §v1.17.0](BENCHMARK.md)。

### 什么场景该开多线程（`threads > 1`）

- ✅ **单条任务有真实计算量**（如 4KB 模板渲染、富文本处理、图片/加解密、签名）：并行线性加速，约核数倍。
- ✅ **CPU 密集的批量跑批**（结算、报表、清洗）：`mapBatch` + `threads≈核数`。
- ✅ **多账户/多分片之间相互独立**的工作：组间并行、组内串行，无共享可变状态。
- ❌ **单条 < 1μs 的极轻任务**（如拼接 120B 短串）：并行开销与任务同量级，倍率 0.7~1.4× 抖动，等于没提速甚至变慢——直接串行或 `CurlMulti`（纯网络）。
- ❌ **需要严格顺序的状态机 / 单账户流水**：先分片到同一任务再串行，别并行。
- ❌ **纯等网络无计算**：用 `CurlMulti`，不要开线程。

> 一句话：**要提速就开 `threads≈核数`；要顺序可预测/最低内存才用 `threads=1`；极轻或纯网络任务并行无益。**

## 十、WorkerPool vs ThreadPool：两种线程池怎么选

本库提供**两个**真线程池，区别只在**派发语义**：

| 维度 | `WorkerPool` | `ThreadPool`（v1.18.0 新增） |
|------|-------------|------------------------------|
| `submit()` 行为 | 槽位满时**阻塞调用方**直到有空位 | **永不阻塞**，任务进队列立即返回 Future |
| 线程模型 | N 个线程按需轮询派发 | N 个**常驻**线程，空闲时从队列自行拉取 |
| 批量合并 | ✅ `map` 自动批量、`mapBatch` 显式批量 | ❌ 逐任务序列化（吞吐更低） |
| 预排海量任务 | 会阻塞在最后一个满槽 | ✅ 一口气入队数万任务不卡调用方 |
| 协程 / 事件循环内派发 | 阻塞会卡住事件循环 | ✅ 非阻塞，适合同步点再 `get()` |
| 原始吞吐（高频短任务） | 高（批量合并） | 较低（逐任务序列化） |
| 适用 | 常规并行映射、最高吞吐 | 生产者快于消费者、非阻塞提交、常驻线程复用 |

实测（8 线程 / 11 核，2,000 个中等 CPU 任务）：串行 56ms、**`ThreadPool.map` ≈3.0×**、**`WorkerPool.map` ≈4.7×**；
非阻塞提交 20,000 个任务 `submit()` 合计 ≈18ms（≈0.9µs/submit），提交后队列积压 19,992 个。

**一句话选型**：

- 要**最高原始吞吐**的高频短任务 → `WorkerPool::mapBatch()`。
- 常规并行映射（生产者-消费者速度相当）→ `WorkerPool::map()`。
- 要**非阻塞提交 / 预排海量任务 / 在协程或事件循环里派发** → `ThreadPool`。

```php
use Kode\Parallel\Pool\ThreadPool;

$pool = new ThreadPool(8);                 // 8 个常驻工作线程
// 非阻塞：一口气预排，调用方不等待
foreach ($jobs as $i => $job) {
    $futures[$i] = $pool->submit($job, ['x' => $i]);
}
// 需要时再阻塞取结果（或交给事件循环）
$results = Futures::all($futures);
$pool->close();
```

> `ThreadPool` 派发/回收完全由调用方线程惰性驱动（不依赖跨线程通道，无 rendezvous 死锁风险）；
> 底层仍是 ext-parallel 真线程，环境要求与 `WorkerPool` 一致（ZTS + ext-parallel）。任务闭包需使用业务类时，
> 构造时传 `bootstrap`（如 `__DIR__.'/vendor/autoload.php'`）。

## 十一、跨线程 / 跨进程的数据同步

每个线程是独立解释器，PHP 变量（全局、静态、单例）、资源、自动加载器**默认不共享**；
任务间只能靠「参数传入 / 返回值传出 / 同步原语协调」三条通道。完整坑点与正确写法见
[跨线程-跨进程数据同步](CROSS_PROCESS.md)：何时用 `Atomic`/`Lock`/`Semaphore`/`Barrier`、
为什么 `Channel` 不能跨进程、为什么「静态变量全局累加」不生效。
